# tisqlx

An async, pure-Rust SQL toolkit built **specifically for [TiDB]**, inspired by
[sqlx] but written from scratch. Runs on **tokio** with **rustls**, and supports
nothing else.

**Requires TiDB 8.5 or newer** (the 8.5 LTS). Older servers are refused at connect time;
`require-tidb=false` connects anyway, untested.

- **Compile-time checked queries** (`query!`, `query_as!`, `query_scalar!`, `query_file*!`) checked
  against a live TiDB, or against offline data generated by `tisqlx prepare`.
- **TiDB-native transactions**: pessimistic/optimistic mode per transaction, stale reads
  (`AS OF TIMESTAMP`, bounded staleness), causal consistency, and automatic retry of the whole
  transaction on write conflicts and deadlocks (`Pool::transaction`).
- **Migrations that match TiDB's semantics.** DDL is never transactional in TiDB, so every
  migration is recorded as *dirty* before it runs. A failure blocks later runs until it is
  repaired.
- A connection pool that spreads over several TiDB servers and skips failed ones, nested
  transactions via savepoints, and a prepared-statement cache that
  survives DDL (also DDL run on another TiDB node).
- `BulkInsert`: stream rows into multi-row `INSERT`s sized to TiDB's packet and transaction
  limits. With `IGNORE`, `REPLACE` or `ON DUPLICATE KEY UPDATE`.
- `Acquire`: write a function once and call it with `&pool`, `&mut conn` or `&mut tx`. Its
  `begin()` is a transaction, or a savepoint inside a transaction.
- `#[tisqlx::test]`: async tests that each get a throwaway database, with migrations and fixtures
  applied.
- Exposes TiDB primitives: `Tso`, `TiDbVersion` feature detection, `AUTO_RANDOM` ids through
  `last_insert_id()`, `tidb_read_staleness`, `tidb_isolation_read_engines` (TiFlash) and
  resource groups.

```rust
use tisqlx::{Isolation, Pool, RetryPolicy, StaleRead, TxnMode, TxnOptions};
use std::time::Duration;

let pool = Pool::connect("tidb://root@127.0.0.1:4000/app").await?;

// Checked at compile time: column types, nullability, bind count.
let user = tisqlx::query!("SELECT id, name, email FROM users WHERE id = ?", id)
    .fetch_one(&pool).await?;          // user.id: i64, user.name: String, user.email: Option<String>

// Optimistic transaction, retried on TiDB write conflicts (9007, 8002, 1213, ...).
pool.transaction_with(&TxnOptions::optimistic(), RetryPolicy::default(), |tx| Box::pin(async move {
    tisqlx::query!("UPDATE accounts SET balance = balance - ? WHERE id = ?", 10, from).execute(&mut **tx).await?;
    tisqlx::query!("UPDATE accounts SET balance = balance + ? WHERE id = ?", 10, to).execute(&mut **tx).await?;
    Ok::<_, tisqlx::Error>(())
})).await?;

// Isolation and mode together.
let tx = pool.begin_with(&TxnOptions::ReadWrite { mode: Some(TxnMode::Pessimistic), isolation: Some(Isolation::ReadCommitted) }).await?;

// With an error type tisqlx can't implement `Retryable` for (e.g. anyhow):
pool.transaction_retry_if(&TxnOptions::optimistic(), RetryPolicy::default(),
    |e: &anyhow::Error| tisqlx::error::is_retryable(e.as_ref()),
    |tx| Box::pin(async move { /* ... */ Ok::<_, anyhow::Error>(()) })).await?;

// Read-only stale read, served by the nearest replica.
let mut tx = pool.begin_with(&TxnOptions::stale_read(StaleRead::MaxStaleness(Duration::from_secs(5)))).await?;
```

## Connection URL

`tidb://user:pass@host:4000/db?ssl-mode=verify-identity&txn-mode=optimistic&resource-group=rg1`
(`mysql://` is accepted too; the user defaults to `root`, the host to `localhost`, the port to 4000).

| query key | default | meaning |
|---|---|---|
| `ssl-mode` | `preferred` | `disabled`, `preferred`, `required`, `verify-ca` or `verify-identity` |
| `ssl-ca` | webpki roots | PEM file of CA certificates for the two `verify-*` modes |
| `socket` | | path of a Unix socket to use instead of TCP |
| `connect-timeout` | `30` | seconds |
| `timezone` | `+00:00` | session `time_zone`; `server` keeps the server's (see *Time zones* below) |
| `txn-mode` | server's | `pessimistic` or `optimistic` |
| `resource-group` | | TiDB resource group of the session |
| `statement-cache-capacity` | `100` | prepared statements cached per connection; `0` disables the cache |
| `require-tidb` | `true` | `false` also accepts TiDB older than 8.5 and servers that aren't TiDB |
| `load-balance-dns` | `false` | see below |

Any other key is set as a session variable, e.g. `?tidb_isolation_read_engines=tikv,tiflash`.
Values are percent-decoded, and `+` is a literal plus (`timezone=+08:00`).

**Several TiDB servers.** List them in the URL (`tidb://user@tidb-0:4000,tidb-1:4000,tidb-2/db`;
hosts without a port use 4000) or with `ConnectOptions::hosts`.
- **Balancing:** a `Pool` opens each new connection on the server with the fewest of its
  connections.
- **Failover:** a server that fails to connect is skipped for a while, with backoff from 1 s up
  to 30 s.
- **Timeouts:** each attempt gets its share of `connect-timeout`, so an unresponsive server
  can't use it all up.
- **No failover on other errors:** only network errors move on to the next server; a wrong
  password fails at once.
- **Single connections:** `TiConnection::connect` tries the servers in order.
- **One DNS name with several addresses** (e.g. a Kubernetes headless service): add
  `load-balance-dns=true` to balance over its addresses.
- **Moving existing connections:** they stay where they are, so after an outage a recovered
  server fills up again as connections are replaced or added.
- **Monitoring:** `Pool::host_connections()` shows the spread, and `server_addr()` on a
  connection says where it landed.

**Bulk inserts.** One row per `INSERT` is the slowest way to load TiDB. `BulkInsert` batches
rows into multi-row prepared statements. Measured with 10 connections: about 20× more rows per
second than row by row, on the local playground cluster (209 000 vs 10 200 rows/s).

```rust
use tisqlx::BulkInsert;

// All at once, or streamed with `start()` / `push()` / `finish()`:
let rows = users.iter().map(|u| (&u.name, &u.email));
BulkInsert::new("users", &["name", "email"]).execute(&pool, rows).await?;
```

- **Batch size:** up to 1000 rows, and within the byte budget read from the server
  (`max_allowed_packet`, and a quarter of `txn-total-size-limit`). Full batches reuse one
  prepared statement.
- **Failures outside a transaction:** each batch commits on its own. When one fails,
  `rows_written()` says how many rows the earlier batches committed, and the writer stops.
- **Inside a transaction** (`execute(&mut tx, …)`): the load is all or nothing, but it must then
  fit TiDB's transaction size limit.

**Pool checkouts** ping a connection only if it sat idle for at least `ping_after_idle`
(default 30 s). A connection used moments ago is handed out as is. If the server dropped it
in the meantime (a restart or a `KILL`), that one query fails and the pool discards the
connection. `PoolOptions::ping_after_idle(Duration::ZERO)` pings on every checkout, and
`test_before_acquire(false)` never pings.

## Query macros

Set `DATABASE_URL`, either in the environment or in a `.env` file in the crate or one of its
ancestors. Nullability comes from TiDB's column metadata: TiDB keeps `NOT NULL` accurately,
and drops it for the nullable side of outer joins and for `MAX`/`MIN`/`SUM`/`AVG`. Override it
in the column alias:

| alias | meaning |
|---|---|
| `` AS `col!` `` | force non-null |
| `` AS `col?` `` | force `Option` |
| `` AS `col: MyType` `` | decode as `MyType` (any `Decode` type, e.g. a `#[derive(Type)]` enum) |
| `` AS `col: _` `` | infer from the struct field (`query_as!` only) |

**Bind arguments** are checked by count, and by type where tisqlx can tell what a `?` stands for.
TiDB reports every parameter as a string, so the macros read it from the SQL instead: the column
a `?` is compared with or assigned to. They then ask the server for that column's type, by
preparing (never running) `SELECT <those columns> FROM <the query's FROM>`.

- **Recognised:** `col = ?` and the other comparisons, `[NOT] LIKE`, `IN (?, …)`,
  `BETWEEN ? AND ?`, `SET col = ?`, `INSERT … (cols) VALUES (?, …)` and `LIMIT`/`OFFSET ?`.
- **Not recognised:** anything else, such as a function argument, a subquery or the select
  list, keeps only the `Encode` bound.
- **Skipping the check:** `value as _` skips it for one argument; see the workarounds below.
- **The check is by kind, and strict on purpose.** TiDB accepts almost any bound type and
  converts it at runtime. Measured on 8.5.8:
  - in a comparison, a mismatched value never errors: `WHERE id = 'abc'` or
    `WHERE created_at > 5` silently matches nothing, with only a warning;
  - in a write, the outcome depends on the value: `'5'` into a BIGINT works, `'abc'` fails.

  So the check rejects any argument whose kind differs from the column's, before the value
  can do either.
- **Types tisqlx can't classify** are never rejected. That covers hand-written `Encode` impls,
  generic arguments, and derived newtypes around such types.
- **Offline data:** the inferred types are stored in `.tisqlx/`, so offline builds check the same
  thing.

Arguments accepted for each column type. `&T`, `Option<T>`, `Box<T>`, `Arc<T>` and
`#[derive(Type)]` newtypes count as their inner `T`; a derived enum counts as text.

| Column next to the `?` | Accepted arguments |
|---|---|
| `TINYINT`…`BIGINT` (incl. `UNSIGNED`), `BOOLEAN`, `DECIMAL`, `FLOAT`, `DOUBLE`, `BIT`, `YEAR`, and `LIMIT ?`/`OFFSET ?` | `i8`…`i128`, `u8`…`u128`, `f32`, `f64`, `bool`, `Decimal`, `BigDecimal` |
| `CHAR`, `VARCHAR`, `TEXT`, `ENUM`, `SET`, `VECTOR` | `&str`, `String`, `Cow<str>`, `types::Set`, `types::Vector`, `uuid::fmt::Hyphenated`, derived enums, and JSON values (`serde_json::Value`, `Json<T>`, `&RawValue`) |
| `BINARY`, `VARBINARY`, `BLOB` | `&[u8]`, `Vec<u8>`, `[u8; N]`, `Cow<[u8]>`, `uuid::Uuid`, and everything accepted for text |
| `JSON` | `serde_json::Value`, `Json<T>`, `&RawValue`, and text (it must be valid JSON) |
| `DATE` | `chrono::NaiveDate`, `time::Date`, and the datetime types |
| `DATETIME`, `TIMESTAMP` | `NaiveDateTime`, `DateTime<Utc \| FixedOffset \| Local>`, `time::PrimitiveDateTime`, `time::OffsetDateTime`, and the date types |
| `TIME` | `chrono::TimeDelta`, `NaiveTime`, `time::Time`, `time::Duration`, `std::time::Duration` |
| `GEOMETRY`, or a position the macros don't analyse | anything that implements `Encode` |

**When the value has another type.** For example, an id that arrives as a `String`:

1. **Convert in Rust (preferred).** The error then surfaces where the input is parsed:
   ```rust
   let id: i64 = id.parse()?;
   query!("SELECT name FROM users WHERE id = ?", id)
   ```
   Likewise `NaiveDate::parse_from_str(s, "%Y-%m-%d")?`, `serde_json::from_str(s)?`, and
   `Uuid::parse_str(s)?`.
2. **Convert in SQL.** A `?` inside a function call is not checked, and TiDB converts explicitly:
   ```rust
   query!("SELECT name FROM users WHERE id = CAST(? AS SIGNED)", id_text)
   ```
   Other conversions: `STR_TO_DATE(?, '%Y-%m-%d')`, `CAST(? AS JSON)`, `UNHEX(?)`,
   `FROM_UNIXTIME(?)`. Unlike an implicit conversion, an explicit one fails or warns predictably.
3. **Skip the check for one argument:** `query!("… WHERE id = ?", id_text as _)`. TiDB then
   converts implicitly at runtime, with the hazards described above.
4. **A domain type:** implement `Type` and `Encode` by hand. A type tisqlx can't classify is not
   checked; use `#[derive(Type)]` instead to be checked like the inner type.
5. **No compile-time check at all:** the runtime API, `tisqlx::query("…").bind(v)`.

**Offline builds (CI):** run `tisqlx prepare` with a database available and commit
`.tisqlx/`. Then build with `TISQLX_OFFLINE=true`. `tisqlx prepare --check` fails when the
data is stale.

## Type mapping

| TiDB | Rust | feature |
|---|---|---|
| `BOOLEAN`/`TINYINT(1)`, `BIT(1)` | `bool` | |
| `TINYINT`..`BIGINT` (`UNSIGNED`) | `i8`..`i64` (`u8`..`u64`) | |
| `BIT(n)`, `YEAR` | `u64` (or `Vec<u8>`), `u16` | |
| `FLOAT`, `DOUBLE` | `f32`, `f64` | |
| `DECIMAL` | `Decimal` (up to ~28 significant digits; a wider value is an error, not rounded), `BigDecimal` (any precision, up to TiDB's 65), `i128`/`u128` (integral values), `f32`/`f64` (rounded) | `decimal`, `bigdecimal` |
| `CHAR`, `VARCHAR`, `TEXT` | `String`, `&str`, `Cow<str>`, `Box<str>`, `Arc<str>` | |
| `BINARY`, `VARBINARY`, `BLOB` | `Vec<u8>`, `&[u8]`, `[u8; N]`, `Box<[u8]>`, `Arc<[u8]>` | |
| `ENUM` | `String`, or a `#[derive(Type)]` enum | |
| `SET` | `types::Set` (list of members), `String` | |
| `JSON` | `serde_json::Value`, `Json<T>`, `&RawValue` | |
| `VECTOR` | `types::Vector` (`Vec<f32>`) | |
| `DATE` | `chrono::NaiveDate`, `time::Date` | `chrono`, `time` |
| `DATETIME` | `chrono::NaiveDateTime`, `time::PrimitiveDateTime` | `chrono`, `time` |
| `TIMESTAMP` (or `DATETIME`) as an instant | `chrono::DateTime<Utc>`, `DateTime<FixedOffset>`, `DateTime<Local>`, `time::OffsetDateTime` | `chrono`, `time` |
| `TIME` | `chrono::TimeDelta`, `time::Duration`, `std::time::Duration` (≥ 0); `NaiveTime`/`time::Time` within a day | `chrono`, `time` |
| `BINARY(16)`, `CHAR(36)` | `uuid::Uuid` (bytes or text), `uuid::fmt::Hyphenated` (text) | `uuid` |

The query macros infer chrono types when `chrono` is on, else `time`. They infer `Decimal`, or
`BigDecimal` when `bigdecimal` is on and the column is wider than 28 digits (or `decimal` is
off). `SET` columns become `types::Set`. UUID and VECTOR columns look like binary and text
columns to the macros, so they need an override such as `` AS `id: Uuid` ``.

**Time zones.** TiDB sends and receives DATETIME and TIMESTAMP values as wall times in the
session `time_zone`. Naive types (`NaiveDateTime`, `PrimitiveDateTime`) are those wall times
as they are. Instant types (`DateTime<…>`, `OffsetDateTime`) are converted from and to the
session zone on the client, using the system time zone database:
- **Default (`timezone=+00:00`):** a UTC session, so no conversion and no loss.
- **`timezone=Europe/Paris`, `timezone=server`, …:** values are converted, and decoded values
  carry the session offset (`FixedOffset`, `OffsetDateTime`). Around daylight-saving changes
  a wall time is ambiguous or doesn't exist. TiDB itself then stores a TIMESTAMP one hour off,
  and tisqlx decodes exactly as TiDB interprets it. Keep the UTC default to store instants
  losslessly.
- **The zone is read when the connection opens,** and again after a pool's `after_connect` hook.
  TiDB doesn't report later changes, so after a raw `SET time_zone` call
  `TiConnection::reload_time_zone()`.
- **A zone missing from the client's database** (e.g. a container without tzdata) makes
  instant types fail with an error. Naive types keep working.

## Authentication and TLS

`mysql_native_password` works on every transport. TiDB has no RSA key exchange, so a
`caching_sha2_password` account needs TLS or a Unix socket; tisqlx reports this clearly instead
of failing with "access denied". The default `ssl-mode=preferred` uses TLS whenever the server
offers it. `preferred` and `required` encrypt without verifying the certificate, `verify-ca`
verifies its chain, and `verify-identity` also its host name. Use `verify-identity` for TiDB Cloud.

## Tests with a database

```rust
#[tisqlx::test(migrations = "migrations")]
async fn creates_a_user(pool: tisqlx::Pool) {
    tisqlx::query!("INSERT INTO users (name) VALUES (?)", "a").execute(&pool).await.unwrap();
}

#[tisqlx::test(migrations = "migrations", fixtures("tests/fixtures/users.sql", "tests/fixtures/posts.sql"))]
async fn lists_posts(pool: tisqlx::Pool) {
    // users.sql and posts.sql have run, in that order
}
```

Fixtures are SQL files (several statements allowed) applied after the migrations, in the order
given. Their paths are relative to the crate root, like `migrations`. They are embedded at
compile time, so editing one rebuilds the tests that use it.

Each test gets its own database (`_tisqlx_test_<name>_<hash>`) on the server named by
`DATABASE_URL`. The database is recreated at the start of each run and dropped when the test
returns. If the test panics, it is left in place so you can inspect it.

## CLI

```sh
cargo install --path tisqlx-cli
tisqlx database setup                 # create DB + run migrations (also: create, drop, reset)
tisqlx migrate add -r create_users    # reversible migration
tisqlx migrate run | revert [--all] | info        # run and revert take --dry-run
tisqlx migrate repair 20260101000000 --applied   # after fixing a dirty migration by hand
tisqlx migrate build-script           # build.rs so migrate!() picks up new files
tisqlx prepare [--check]              # offline data for query! macros
```

Every command that needs the database takes `-D <url>` or reads `DATABASE_URL` (a `.env` file
works too). Migrations are read from `./migrations` unless `--source <dir>` says otherwise.

## Development

```sh
make db-up     # dedicated test TiDB v8.5.8 on port 4100 (never a shared server); needs tiup or docker
make test      # unit + mock-protocol + live tests
make ci        # lint, feature sets, tests, offline-data check
```

`cargo test` alone works without a database: live tests skip, and the macros compile from the
committed `.tisqlx/` data. See [TESTING.md](TESTING.md) for the test strategy and
[TODO.md](TODO.md) for the known gaps. The live tests create the databases `tisqlx_t_*` and
`tisqlx_macros`, and two unprivileged accounts, `tisqlx_sha` and `tisqlx_nat`, on the test
server.
